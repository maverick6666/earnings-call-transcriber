# 검수 층: 위험 점수(0층) · 고유명사 제한 교정(1층)

작성 2026-11-24 · 표는 `scripts/review_tables.py`(숫자는 `reports/correction_*.json`)

## 한 줄 요약

**글만 보고 이름을 고치는 교정기는 맞는 글도 망친다.** 정답 글(= 완벽한 받아쓰기)에 걸어 보니, 용어집 · 유사도 ·
대소문자 규칙만으로는 낱말의 1.23%(고유명사 낱말의 2.81%)를 틀리게 바꿨다. 모양만 바꾸는 편집을 거르고(규칙 6),
흔한 낱말이 걸린 바꿈에는 위험 근거를 요구하니(규칙 7) 처음 보는 33통화에서 0.10%(고유명사 1.31%)로 줄었다.
**실제 받아쓰기를 얼마나 고치는지, 위험 점수가 단어 확률(AUC 0.79)보다 나은지는 아직 재지 않았다** — 받아쓰기 결과와
창별 저장본이 있는 PC 에서 돌릴 순서를 5절에 적었다.

## 1. 왜 이런 모양인가

| 근거 | 이 저장소에서 |
|---|---|
| LLM 에 받아쓰기를 통째로 고쳐 쓰게 하면 음성에 없는 말로 바꾸거나 지어낸다(Ma et al. 2023 · ClozeGER, ACL 2024 Findings · RLLM-CF 2025) | LLM 은 **고유명사 편집을 제안만** 하고, 받아들일지는 규칙이 정한다 |
| RECOVER(2026): 바꿀 말은 용어집에 있어야 하고, 일반 수정은 금지, 철자 유사도 하한 → Earnings-21 고유명사 WER 23.8 → 15.9, 전체 WER 그대로(Whisper-small) | 같은 규칙(1~5)에서 출발 |
| 단어 확률은 맞고 틀림을 잘 못 가른다(이 저장소 실측 AUC 0.72~0.82) | 0층: 확률 + 겹친 창 일치 + 어휘 · 시간 특징 + (선택) 다른 모델 |
| 용어집에 엉뚱한 이름이 섞이면 효과가 사라진다(이 저장소 +P, arXiv 2608.05759, ConEC) | 후보는 구간마다 걸러서 넘기고, 정답 글 실험은 oracle · noisy 둘 다 |

## 2. 0층: 위험 점수 (`src/callscribe/detect.py`)

낱말마다 '틀렸을 확률' 을 매긴다. 받아쓰기를 다시 돌리지 않고 이미 있는 것만 쓴다.

- **단어 확률** · 앞뒤 1낱말 중 가장 낮은 확률
- **겹친 창 일치**: O1 은 모든 지점을 창 두 개가 받아 적는다. 결과에 쓰지 않은 쪽 창이 같은 자리(±1초)에 같은 낱말을
  적었나. 공짜 두 번째 의견이다(같은 모델이라 다양성은 작다 — O2 투표가 이득이 없던 이유).
- **다른 모델 일치(선택)**: small · large-v3 O1 결과가 이미 있으니 turbo 의 두 번째 의견으로 쓸 수 있다.
- **어휘 · 시간**: 숫자 · 문장 가운데 대문자 · 약어 · 글자 수 · 글자당 길이 · 같은 낱말 되풀이 · 용어집과 비슷하지만 다름
- 라벨: 정답과 정렬해 바꿈 · 끼어듦이면 1. **빠진 낱말은 받아쓰기에 자리가 없어 이 점수로 직접 못 잡는다**(따로 센다).
- 모델: 표준화한 특징의 L2 로지스틱 회귀. **통화 하나씩 빼고** 학습해 그 통화를 점수 매긴다.
- 보고하는 숫자: AUC, 낱말 상위 5 · 10 · 20%, **듣는 시간 예산**(사람이 녹음 길이의 10 · 20 · 30% 만 위험 높은 곳부터
  들을 때 틀린 낱말 중 잡히는 비율), 같은 예산에서 고유명사 · 숫자 오류를 잡는 비율. 검수 비용은 시간이라 마지막 두
  숫자가 실제 쓰임에 가깝다.

시뮬레이션 통화로 스크립트가 끝까지 도는 것만 확인했다(가짜 모델은 확률이 맞고 틀림을 알려 주게 만들어져 있어 숫자에
뜻이 없다).

## 3. 1층: 고유명사 제한 교정 (`src/callscribe/entity_fix.py`)

    구간(약 45초) → 용어집 후보 찾기(글자 + 가벼운 발음 열쇠, 한국어는 자모) → 고칠 후보가 있는 구간만 제안 받기
    → 규칙 검사 → 적용(시각은 원래 낱말 것, 원래 글은 original 에)

| 규칙 | 거르는 것 | 예 |

| 1 | 바꿀 말이 용어집에 없음 | – |
| 2 | 원래 말이 그 구간에 없음 | – |
| 3 | 대소문자 · 띄어쓰기만 다름 | 'Monro,' → 'Monro' |
| 4 | 글자 · 발음이 안 비슷함(0.6, 3글자 이하 0.85) | 'star' → 'Cytiva' |
| 5 | 원래 말이 이미 용어집의 다른 이름 | 'BMO' → 'Monro' |
| 6 | 모양만 바꿈: 낱말 · 조각 더하기 빼기, 복수 · 소유격, 쉼표 · 마침표를 넘음, 받아 적은 숫자 바꾸기, 겹치는 낱말 뺀 나머지가 안 비슷함 | 'financial' → 'Voya Financial', 'Affimed's' → 'Affimed', 'Johnny, uh, so.' → 'John Hess', 'Phase III' → 'Phase II', 'Eversource in' → 'Eversource Energy' |
| 7 | 흔한 낱말(다른 통화 3개 넘게 나오는 낱말)이 걸렸는데 그 자리에 0층 위험 표시가 없음 | 'as' → 'ASA', 'operating' → 'Operations' |
| 8 | 원래 말이 4낱말 넘음 · 겹치는 편집 | – |

제안자는 둘이다. **FuzzyProposer**(LLM 없이 유사도 0.8 이상이면 바꿈 — 기준선)와 **LLMProposer**(Anthropic Messages
API, 답은 `cache/llm/` 에 저장). LLM 은 아직 돌리지 않았다.

## 4. 정답 글 실험: 교정기가 맞는 글을 얼마나 망치나

받아쓰기 자리에 **정답 글을 그대로** 넣었다. 고칠 것이 없으니 바꾼 자리는 전부 과교정이다. 모델 · 녹음 없이 잴 수 있어
여기서 먼저 했다. 제안자는 기준선(FuzzyProposer), 용어집은 +P 와 같은 oracle(그 통화에 나오는 말 최대 40개) · noisy
(같은 수의 엉뚱한 이름을 섞음). 흔한 낱말은 그 통화를 뺀 Earnings-21 정답 전사문에서 셌다. 0층 점수가 없으니
**규칙 7 은 흔한 낱말이 걸린 바꿈을 모두 버리는 쪽**으로 작동한다.

| 받아쓰기 | 통화 | 용어집 | 규칙 | 바꾼 자리 | WER | 고유명사 오류 | 숫자 오류 |

| 정답 글 | Eval-10 (11) | noisy | + 규칙 7 | 7 | 0 → 0.01% | 0 → 0.09% | 0 → 0.00% |

### 읽는 법

- **기본 규칙만으로는 위험하다.** 용어집이 완벽해도(oracle) 고유명사 낱말의 2.4% 를 망쳤다. 교정기가 실제 받아쓰기에서
  고유명사 오류 18.7% 중 몇 %p 를 고쳐도, 맞던 이름을 이만큼 망치면 이득이 크게 준다.
- 망친 것의 대부분은 흔한 낱말을 비슷한 이름으로 바꾼 것이었다(Eval-10 첫 실험: 'as' → 'ASA' 65번, 'at' → 'AT&T'
  50번, 'operating' → 'Operations' 45번). 규칙 6 · 7 을 더해 처음 보는 33통화에서 바꾼 자리를 93% 줄였고
  (2,764 → 186), 그중 대부분이 규칙 7 몫이다(1,954 → 186).
- **규칙 6 · 7 은 Eval-10 의 과교정을 보며 만들었다.** 그래서 Eval-10 숫자(바꾼 자리 7)는 낙관적이다. 정직한 숫자는
  규칙을 만들 때 보지 않은 **33통화 쪽**이다(186, 통화당 5.6자리).
- **남은 과교정은 글만으로는 못 가린다.** 처음 보는 33통화에서 남은 것은 둘 다 실제 이름인 경우('Concho' → 'Conoco',
  'Michele' → 'Michelle', 'Juan' → 'JAN')와, 흔한 낱말 목록에 못 든 업계 낱말('megawatts' → 'Gigawatts', 'genomic' →
  'Genome')이다. 앞은 소리(3층) · 참석자 명단 · 0층 위험 근거가, 뒤는 더 큰 전사문 묶음(흔한 낱말 목록)이 필요하다.
- **규칙 7 은 고칠 것도 막는다.** 'in video' → 'Nvidia' 처럼 흔한 낱말로 잘못 들린 이름은 0층 위험 표시가 없으면 못
  고친다. 정답 글 실험은 고칠 것이 없어서 이 손해를 못 잰다 — 실제 받아쓰기에서 `--risky-top` 과 함께 재야 한다.

## 5. 다음에 돌릴 것 (받아쓰기 결과 · 창별 저장본이 있는 PC)

```bash
# 0층: 위험 점수가 단어 확률보다 나은가 (모델 · 그래픽카드 없이, 저장된 결과만)
python scripts/eval_detector.py --model large-v3-turbo
python scripts/eval_detector.py --model large-v3-turbo --alt small       # 다른 모델을 두 번째 의견으로

# 1층: 실제 받아쓰기에서 고치는 것 · 망치는 것
python scripts/eval_correction.py --model large-v3-turbo --proposer fuzzy --glossary noisy --risky-top 0.2
ANTHROPIC_API_KEY=... python scripts/eval_correction.py --model large-v3-turbo --proposer llm --glossary noisy --risky-top 0.2
python scripts/review_tables.py
```

정할 것
- 0층 '전부' AUC 가 '확률만'(≈0.79)보다 뚜렷이 높고, 듣는 시간 20% 에서 고유명사 · 숫자 오류를 절반 넘게 잡는가.
  못 미치면 1층을 위험 표시에 묶는 설계(규칙 7)를 다시 생각한다.
- 1층에서 '고침 − 망침' 이 양수이고 고유명사 오류가 +P(oracle 16.1%)만큼 내려가는가. LLM 이 기준선보다 망침을
  얼마나 줄이는가.

## 6. 한계

- 실제 받아쓰기 · LLM 결과가 없다. 위 표는 '교정기가 맞는 글을 얼마나 망치나' 만 잰다.
- 용어집은 Earnings-21 의 bias_lists 에서 고른 것이라 일반 낱말('Operations', 'Price')이 섞여 있다. 회사별로 모은
  용어집이면 과교정이 줄 것으로 보지만 재지 않았다.
- 흔한 낱말 목록은 Earnings-21 정답 43통화로 만든 작은 것이다. 실제로는 지난 통화 전사문 묶음이 이 자리를 채운다.
- 한국어는 자모 유사도만 넣었고 시험하지 않았다(공개 한국어 어닝콜 정답 자료가 없다).
